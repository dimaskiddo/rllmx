# PRD 06 — OAuth & Token Refresh (`app/oauth/`)

**Status:** partial · **Steps:** 1.9a, 1.9b, 1.9c, 1.10c to 1.10f

Step 1.9 brings the framework and the two seed providers (`claude`, `codex`); the rest add a data file and post-login hooks in 1.10. It is built in three parts: **1.9a** the login (sessions, token client, routes, callback page, listener; built), **1.9b** the refresh (proactive, reactive, background, the expired mark, the connection test; built, and a login's token now goes as a bearer token), **1.9c** the headers a login's token carries, the client tool and the Claude disguise (built).

### Connect Flows

A provider's flow is data (`oauth.flow` in its file), run by one engine per kind.

`app/oauth` holds the `code-pkce` flow since 1.9a (claude and codex), the RFC 8628 `device` flow since 1.10c (github) and, since 1.10e, the `code` flow without PKCE (cline, clinepass) and the `code-pkce` logins xai and gitlab. Every other flow below is the design the later 1.10 steps implement.

### Device Login (built in 1.10c)

A device provider's `oauth` block has `flow: device`, `deviceUrl` and `tokenUrl` (both https), `scope`, and no authorize address, redirect, exchange or parameters; a refresh block is optional (a provider that never renews its token has none).

| Item | Behavior |
|---|---|
| Start | `GET /api/oauth/{provider}/device-code` posts the client id and scope to `deviceUrl` as a form and answers `{state, userCode, verificationUri, expiresIn, interval}`. The device code is kept in the server-side session and never returned. The answer must hold a device code (at most 1 KiB), a user code of at most 64 characters, and a plain https page without credentials; the interval is 1 to 60 s (default 5 s), the lifetime up to 30 min (default 15 min) |
| Poll | `POST /api/oauth/poll` with `{state}`. The session is bound to the dashboard session that started it, like the redirect flows. The router asks the provider at most once per interval whatever the browser sends, and two simultaneous polls make one call (`Sessions.Poll` hands the login to one caller and the rest read `pending`). `authorization_pending` and `slow_down` come back in a 200 body or an error status, so the body is read first; `slow_down` adds 5 s to the interval, capped at 30 s. A finished login answers once, then `unknown` |
| End | `expired_token`, `access_denied`, any other provider error or a body with no access token end the login with a fixed word (`expired_token`, `access_denied`, `rejected`, `transport`); provider text is never kept |
| Hook | After the tokens arrive, the `hook` named in the data runs from the table in `app/oauth/hooks.go` and returns the account's email and provider data. A hook never fails a login: what it cannot learn it leaves out. A test keeps the table equal to `upstream.HookNames` |

### Copilot Token (built in 1.10c)

A GitHub login token cannot call the Copilot API. The data's `mint: copilot` and `endpoints.copilotToken` make the login's token a source for a second credential, and that credential is the one a request carries.

| Item | Behavior |
|---|---|
| Mint | `GET` the endpoint with `Authorization: token <login token>` and the data's `user-agent`, `editor-version`, `editor-plugin-version` and `x-github-api-version` headers (the chat-only headers are not sent). Only `token` and `expires_at` are read; the token is at most 4 KiB with no control character |
| Keeping | `oauth.Minter` serves the stored token while more than five minutes of it remain, else mints. One mint is in flight per account (`cache.Load` on the memory-only `connections` group, 10 s) however many requests ask. The token is also written sealed to `providerSpecificData.copilotToken` with its expiry, so a restart does not mint for every account at once |
| Refusal | A 401 or 403 from the chat endpoint asks for one new token (`Minter.Renew`, which hands back a token another request already replaced without a call) and sends the same body once more. A refused token is never sent twice |
| Failure | A mint that fails is the account's failure with a fixed text (`transport` gives 502, any other 401 "no credentials"); nothing the provider said, and no token, is logged, stored in an error or returned |
| GitHub profile | `GET` the `user` endpoint with the login token. Login name, display name, email and numeric id are stored (short text only, no control characters). The email is often hidden, so a login with a `githubUserId` is the same account as an earlier row with that id (divergence 235) |

### Login Data and Steps (steps 1.10c to 1.10f)

Nothing provider specific is code that data cannot name. A provider file's `oauth` block picks from fixed tables, and a test keeps each table equal to the schema's allowed names. Built in 1.10c: `flow: device`, `deviceUrl`, `hook: github`, `mint`, `endpoints`. Built in 1.10d: `callHeaders` with the device id, device `params`, `endpoints.verify`, `dialect: kilocode`, `noClient`, `refresh.tokenHeader`, `refresh.hook`, and the hooks `muse`, `nous`, `kilocode` and `grokCli`. Built in 1.10f: the device dialects `codebuddy`, `minimax` and `zcode`, a dialect renewal, `refresh.fields`, and device state kept in the server session. Built in 1.10e: `flow: code`, `redirect: public`, `redirectHost`, `appFromAccount`, `pat`, `refresh.url`, the code dialect `cline`, authorize-parameter placeholders, and the hooks `xai` and `gitlab`. The rows marked *later* are still design.

| Data field | Meaning |
|---|---|
| `hook` | A step after the tokens arrive (`app/oauth/hooks.go`). Built: `codex`, `github`, `muse`, `nous`, `kilocode`, `grokCli`, `xai`, `gitlab`. Later: `iflow`. A step returns the email, extra `providerSpecificData` and what it changes about the stored credential: the access token (`Access`), the key a request carries (`APIKey`), whether the login can be renewed (`NoRefresh`) and an earlier expiry (`ExpiresAt`). A step returns an error to end the login with a fixed word and never repeats provider text. Fatal: `muse` (no key, no login). Best effort: `github`, `nous`, `kilocode`, `grokCli`, `xai` (id token claims, no call), `gitlab` (`GET` the user endpoint of the account's server) |
| `dialect` | A device login whose start and poll do not follow RFC 8628 (`app/oauth/device_dialect.go`), or a `code` login whose exchange and renewal are not plain token calls (`app/oauth/code_dialect.go`). Built: `kilocode`, `codebuddy`, `minimax`, `zcode`, `kiro` (device), `cline` (code), `kiro-social` (code-pkce). Later: code style `iflow`. `codebuddy` and `zcode` have no client id and no PKCE; `minimax` sends a PKCE challenge, and when the start answer has no device code the user code is polled instead. `codebuddy` also owns its renewal (the refresh token in `X-Refresh-Token`, an empty JSON body, a camelCase answer; only a 401 means the sign-in is gone). `zcode` trades the Z.ai token for a coding-plan key in the poll (business login, personal organisation and project, the key named `zcode-api-key`, made when missing, and its secret half) and stores only that key. A dialect builds the tokens, never the connection: the engine stores it. A dialect is valid only for its own flow |
| `callHeaders` | Headers on the router's own calls while logging in and renewing: the device start, the poll, the renewal and a hook. A name cannot be a credential or framing header (the same filter as `headers`); a value may hold `{deviceId}` and no other brace. When any value holds it, the start makes one id, keeps it in the server-side login, sends it, and stores it in `providerSpecificData.deviceId`, from where every renewal sends it again. An account without an id leaves that header out. `headers` stays the chat-only set |
| `params` | Extra fields, in the data's order. A device login adds them to the start form after `scope` and `client_id`; a `code-pkce` login adds them to the authorize address after the standard parameters; a `code` login sends **only** these. A `code-pkce` or device login cannot use the login's own names (`state`, `client_id` and so on); a `code` login has none, so it may. A value may hold `{nonce}` (16 random bytes in hex, new for each login), and a `code` login also `{redirect}` and `{state}`; any other brace is refused |
| `basicAuth`, `exchangeEchoState` | Later: Basic client authentication; the login state in the exchange body (Claude only) |
| `endpoints` | Addresses a step calls, by role: `copilotToken`, `user`, `key` (Meta), `agentKey` (Nous), `profile` (Kilo), `verify` (the page to open when the start answer names none, with `?user_code=` added when the answer has a plain code). Each must be https |
| `refresh.tokenHeader`, `refresh.hook` | Built: a header that also carries the refresh token (Nous), and a step run after a renewal from a table of its own (`app/oauth/refresh_hooks.go`; Nous mints a new agent key). A step that fails keeps the key the account holds. Built: `refresh.fields`, extra fields of the standard renewal call (MiniMax Code: `scope`, `audience`), at most four, never the names the call sets itself. `bare`, `tokenField` and `camel` are not needed: the one provider that wanted them (CodeBuddy) renews in its dialect |
| `noPkce`, `slowRefresh` | Built (1.10g). `noPkce` on a `code-pkce` login sends no code challenge and no verifier, for a client registered without them that proves itself with a secret (Google). The secret comes from configuration (`OAUTH_CLIENT_SECRET_GOOGLE`, `OAUTH_CLIENT_SECRET_ANTIGRAVITY`, at most 256 characters, no spaces), is sent on the code exchange and every renewal, and is never logged or returned. `slowRefresh` makes the background pass wait `OAUTH_REFRESH_GOOGLE_DELAY` (12 s, 0 to 1 m) plus 0 to 4 s of random jitter after that account, instead of the common gap |
| `callHeaders` on `code-pkce` | Built (1.10g). The same filter as on the device flow; the Google hooks read them |
| `noClient` | Built: a login with no OAuth client id (kilocode, cline, clinepass), so no `OAUTH_*` variable exists for it. Valid for the device and `code` flows (also codebuddy and glm) |
| `appFromAccount` | Built (gitlab). The OAuth application and server address come with the login request. A `POST /api/oauth/{provider}/authorize` body `{baseUrl, clientId, clientSecret}` is read only for such a provider and refused for any other, and the `GET` form is refused for it (answer 400). The address must be a bare https origin (`upstream.BareOrigin`: host and port, no path, query, userinfo, fragment or trailing slash), the id and secret at most 256 characters without control characters or spaces; the secret is optional. They live in the memory session (`Session.App`); on success `baseUrl`, `clientId`, `authKind: oauth` and the secret (`clientSecret`, already a sealed path) are stored in the account's provider data. `Flow.WithApp` moves `authorizeUrl`, `tokenUrl`, `refresh.url` and every endpoint onto that origin by their path. The refresher builds its flow from the stored application, so such an account renews with its own id and secret (divergence 246). Exchange and renewal send `client_secret` only when one is held. Nothing returns the secret or puts it in an address |
| `pat` | Built (gitlab). `POST /api/oauth/{provider}/pat` with `{token, baseUrl}`, for a provider whose data sets it: the token is checked against the user endpoint of the named server, presented as a bearer token (the way chat presents it), then stored with no refresh token and no expiry (`authKind: personal_access_token`). The answer is the account id only |
| `redirectHost` | Built. `localhost` (default) or `127.0.0.1`, only on the `fixed` redirect, for a client registered that way (xai) |
| `refresh.url` | Built. The renewal address when it is not `tokenUrl` (cline), https |

The Copilot token the `github` step mints is stored sealed (`providerSpecificData.copilotToken`), and the Muse and Nous steps store the key that chat requests use as the access token or API key. Meta's account token is not kept.

### Redirect Policy

The reference builds the redirect in the browser as `http://localhost:<window.location.port or 443>/callback`, so behind HTTPS it becomes `http://localhost:443/callback`, and the browser sends `redirect_uri` to the server. Here the **server decides** the redirect and the browser never sends one. A forwarded header or the request origin never builds a redirect.

A redirect must be one the provider's OAuth client registered. Claude and Codex log in with the public client ids of the Claude Code and Codex command line tools, which accept loopback redirects only, so their redirect is a `localhost` address even when the dashboard is on an HTTPS host. This is the link between the router, as OAuth client, and the provider. A Claude Code CLI that uses the router takes no part: it calls `/v1/*` with a router API key. Cloaking shapes later upstream requests and has no part in the login.

| Policy (`oauth.redirect`) | Redirect | Providers |
|---|---|---|
| `fixed` | `http://<redirectHost>:<fixedPort><callbackPath>` (`localhost` unless the data names `127.0.0.1`), served by a listener | codex (`localhost:1455/auth/callback`), xai (`127.0.0.1:56121/callback`) |
| `local` | `http://localhost:<router port>/callback`; the port is the request's own when the request is local, else `APP_PORT` | claude, gemini-cli, antigravity; Zed later |
| `public` | `<public base>/callback`, the base being `APP_URL` or, for a local request with no `APP_URL`, the request's own loopback host (`sso.PublicBase`); an error (400, "set APP_URL") when neither exists. `paste` is false: the router's own callback page receives it. The dashboard must be opened at the `APP_URL` origin or its cookie does not reach `/callback` | gitlab, cline, clinepass |
| none (device flow) | The dashboard shows the verification URL and code | github, kimi, kilocode, qoder and others |

When the browser that finishes a `fixed` or `local` login cannot reach `localhost` of the router (a remote dashboard), the start answer says `paste: true`: after consent the browser lands on a dead page and the user pastes the address from its address bar. The deployer does not register anything for the shipped client ids. Replacing a client id with an app of one's own means registering the redirect the start answer shows. Whether Claude also accepts its hosted code page is still unchecked.

| Item | Behavior |
|---|---|
| Session | `oauth.Sessions`, an in-process map (not the `oauth` cache group: `Begin` has to be one atomic step, which the cache facade cannot give, and the group is memory-only anyway): state, provider, redirect, verifier, fixed port and a binding (device code and interval join in 1.10). At most 1000 logins and 20 per binding; the oldest of a full binding is dropped. The state is 256 random bits. TTL 10 minutes; `Take` makes it single use. The binding is `sso.BindFor(secret, "oauth_bind", <auth_token cookie>)`, so another browser gets the same answer as an unknown state. A login finished by the fixed-port listener has no dashboard cookie to compare; the 256-bit state, which only the provider's redirect brings back, and the listener's port are the proof, and the dashboard still reads the outcome only with its own binding. After the end, a `done` record (connection id or a short error code, no secret) lives 2 minutes and is read once through `status` |
| Routes | All `ClassAlwaysProtected`, behind the CSRF guard. `GET /api/oauth/{provider}/authorize`, `POST /api/oauth/{provider}/authorize` (an application with the request), `POST /api/oauth/{provider}/pat`, `POST /api/oauth/exchange` (`{state, input}`, `input` being a full URL with the code in the query or fragment, a bare code or `code#state`), `POST /api/oauth/callback` (what the `/callback` page posts), `GET /api/oauth/status?state=`, `GET /api/oauth/{provider}/device-code`, `POST /api/oauth/poll`. No route returns a token, a secret or a verifier |
| `/callback` page | `GET /callback`, public, static (`web/static/callback.html` and `web/static/js/callback.js`, following the dashboard layout in `WORKFLOWS.md`). It reads `code`, `state` and `error` from the query or fragment, removes them from the address, and posts them to the server. No `postMessage`, `BroadcastChannel` or storage |
| Listeners | One per fixed port, shared by every login waiting on it, bound to `OAUTH_CALLBACK_HOST` (`127.0.0.1`; `0.0.0.0` in a container). They serve only the callback path, only for a loopback `Host`, only for a state a pending login holds on that port, and finish that login server side. They stop when the last login ends (checked on every release and every 15 s, never within 5 s of the last use) and with the server (`rllmx.oauth` runner). A busy port gives `paste: true` |
| Token calls | `oauth.TokenClient`: JSON or form per the data, answers bounded to 1 MiB, no redirect followed (a moved endpoint would carry the refresh token elsewhere), 15 s per call, on the guarded dialer. Built in 1.9a for the code exchange; the refresh call joins in 1.9b. Failures are reduced to a class (built: `invalid_grant`, `transport`, `rejected`, `malformed`; `refresh_token_reused` is folded into `invalid_grant` and the device classes arrive in 1.10; the login adds the fixed codes `access_denied`, `invalid_input` and `storage`); provider text is never kept, logged or returned. The PKCE verifier (32 bytes from `crypto/rand`), the S256 challenge (`sha256` then base64url, both stdlib) and the authorize URL are our own code; `golang.org/x/oauth2` is not a dependency. Token calls are ours too, because Claude's endpoint takes JSON and a refresh needs the raw error body for classification |
| Client credentials | Configuration (`OAUTH_CLIENT_ID_<PROVIDER>`, `OAUTH_CLIENT_SECRET_<PROVIDER>`), never literals in Go code or provider data (`tests/oauth_clients_test.go` scans `app`, `bootstrap`, `config`, `routes`, `pkg` and `web` for the two public ids by hash, whole words only; `.env.example` carries them). An empty id disables that provider's login and refresh with a clear error before anything is sent. Secrets are redacted in logs by name and never returned by the API |
| Account | Codex reads the email, the ChatGPT account id and the plan from the id token (no signature check: the claims name the account and decide duplicates). A login that repeats an account updates its row by the repository's duplicate rules |

### Refresh

All four triggers use `oauth.Refresher.Refresh` (built in 1.9b). Per provider, the registry's `oauth.refresh` block gives the body encoding (`json` for Claude and Codex), the lead time and, for Codex, the age rule; its `oauth.headers` are the static headers sent on a login's token.

| Trigger | When |
|---|---|
| Proactive | Before each request, when the access token is within the provider's lead time (default 5 minutes; Claude 4 h, Codex 10 min, which also refreshes when the last refresh is older than 8 days). A failure other than a dead token lets the request go on with the old one |
| Reactive | On a 401 or 403 from the upstream: up to three tries (1 s and 2 s apart), the credentials are stored, the same account is called once more. If that fails too, the normal failure path runs on the new answer |
| Background | A loop in the `rllmx.oauth` runner (not a cron job: the schedule facade has no seconds-level first run), started once the data gate opens: first pass after 10 s, then every 5 minutes, one account at a time, for active accounts with a refresh token and a known expiry within the lead time or 30 minutes, whichever is longer. The pause between accounts is `OAUTH_REFRESH_DELAY` (default 1500 ms; `OAUTH_REFRESH_GOOGLE_DELAY` joins in 1.10 with the first provider that sets `slowRefresh`). `OAUTH_BACKGROUND_REFRESH=false` turns it off. A failure logs the provider and the class only |
| Test | `POST /api/providers/{id}/test` for a registry entry with an `oauth` block: refresh when due, then check the token exists and has not expired. A provider without one still answers `test not supported` and writes nothing |

**Safety.** Calls for the same provider and refresh token share one request through `app/cache.Load` on the `refresh` group (single-flight lives there, per AGENTS), with the result kept for 10 s in the memory-only `refresh` group, so 50 concurrent requests make one call. The new credentials are stored by `ConnectionsRepo.SwapCredentials`, one transaction that writes only while the stored refresh token is still the one used. If another request or process rotated it first, nothing is written and the stored row is used; single-use tokens (xAI, MiniMax, Codex) are never spent twice. `invalid_grant` (which includes a reused token) marks the connection `testStatus: expired` with the fixed message "needs to be reconnected", under the same condition (`ConnectionsRepo.MarkExpired`); account selection skips it and nothing calls the provider for it again. **Only a reconnect clears the mark** (the login writes `active`): the refresh token is dead, so neither a refresh nor a test can heal it, and a passing test never overwrites it. A dead account met mid-request is excluded without a lock, since the mark is the stronger state. A request that meets only dead accounts answers **503** "[provider/model] needs to be reconnected", error class `expired`, with no retry hint: a 401 would make the client discard a good router key.

**What a refused request does.** On a 401 or 403 from a login's token the pipeline asks for a renewal (up to three tries, one and two seconds apart, and no call at all when the stored access token is no longer the refused one), then sends the same body once more with the new token. A second refusal is an ordinary account failure. Any other status never triggers a renewal.

## Divergences

Deliberate differences from the references in this area. Numbers are stable and cited from other docs.

| # | What we do differently | Why it is better |
|---|---|---|
| 20, 21, 34 | Redirect per provider from `APP_URL`; one single-use server session per login; ids and secrets as `OAUTH_*`. **(partial)** variables, cache policy exist; flows in 1.9 | Public HTTPS logins cannot redirect to localhost; state always checked; credentials rotate without rebuild |

## Findings

**1.9a built: login only.** A Claude or Codex account can be connected by `GET /api/oauth/{provider}/authorize`, then the callback page, the fixed-port listener or a pasted address. Nothing refreshes a token yet (1.9b) and an OAuth token is still sent as an API key (1.9c), so a connected account does not serve requests until those land.

**The reference trusts the browser; we do not.** It sends the verifier and redirect through the browser, never compares the returned `state`, and lets three channels carry the code. Here the verifier never leaves the process, `Begin` is single use, and a completion needs the state and the binding.

**The listener cannot check the dashboard cookie.** It lives on another port, so a login it finishes is proven by the secret state and the port alone. Cookies do not isolate by port, so a `localhost` dashboard would send its cookie there, but a `127.0.0.1` one would not; relying on it would make the flow depend on how the dashboard was opened.

**An equivalent check was removed.** `routerPort` once re-checked that the request Host was loopback; `IsLocalRequest` already requires it, so the mutant that removed the second check could not fail any test and the check went.

**1.9b built: refresh.** A token is renewed before a request when due, again after a 401 or 403, in the background, and when the account is tested. A login's token is now sent as a bearer token with the provider's static headers (Claude: `anthropic-beta: oauth-2025-04-20`, `anthropic-version`); the computed beta list and the Codex headers are 1.9c.

**A dead refresh token is stored, not retried.** The reference never records `invalid_grant`, so it calls the provider after every cooldown for good. `MarkExpired` writes the mark under the same stored-token condition as the swap, and a test proves exactly one swap wins a race and that a mark never lands on a rotated token. A mark that lands first does not stop a swap of the same token, which only a provider answering both ways could cause. The mark is the stronger state, so a dead account met in a request gets no lock on top.

**Parallel requests make one call.** `cache.Load` collapses concurrent renewals of one refresh token and keeps the result for 10 s; the loader also re-reads the row first, so a token another process already rotated costs no call.

**Two gaps the mutants found.** A non-auth error on a login renewed nothing in the code but nothing proved it, and `Ensure` could have passed an expired account; both have tests now.

**1.10f built: five logins on three device dialects.** CodeBuddy has no client and no device code, so its one state serves as both; MiniMax Code is RFC 8628 with a PKCE challenge and two answer shapes; ZCode is a poll that ends in a key chain. The dialect state (`Verifier`, `DeviceExtra`) stays in the session. Fuzzing found that `clampLife` and `clampInterval` multiplied before capping, so a huge `expires_in` wrapped to a negative duration; they cap first now, which also fixes the Kimi, Nous and GitHub device logins.

**1.10g built: the Google logins.** Gemini CLI and Antigravity are authorization-code logins with no code challenge and a client secret. The hooks read the profile and `loadCodeAssist` (the project as a string or an object; the default tier), and Antigravity then calls `onboardUser` up to four times, three seconds apart, inside the login. A project that did not come at login is looked up on the first request by `oauth.ProjectResolver` (one lookup in flight per account, an hour of result, two onboarding tries 12 s apart) and stored with `ConnectionsRepo.SetProjectID`, which writes only to an empty field. A project id is held to `^[a-z][a-z0-9-]{4,28}[a-z0-9]$` before it enters a path or a body. Nothing invents a project name. Vertex has no login: `oauth.GoogleMinter` signs a one-hour RS256 assertion with the standard library for a service account, refreshes user credentials with their own client, and needs nothing for a raw key; the key text stays in the sealed API key and in memory, never in a log, a cache key or an answer.

**Not verified without a live account (1.10g):** Google accepts the client secrets and the `local` loopback redirect, `loadCodeAssist` returns a project for a fresh account, Antigravity `onboardUser` finishes inside four tries, a Vertex service account and user credentials each get a token, and the partner models answer on the project-scoped address.

**Not verified without a live account (1.10f):** the CodeBuddy state and poll answers on both sites, the MiniMax Code device answers (with and without a device code) and its single-use renewal, and the ZCode key chain, which makes or reuses a key named `zcode-api-key` on the user's Z.ai account.

**Not verified without a live account:** that Anthropic accepts the single `oauth-2025-04-20` beta value alone, and that Codex takes a JSON refresh (the reference registry says form; the code it runs sends JSON).

`app/git` is still open.

**1.9c built: what a login's request looks like.** The provider's data decides every header: the identity set, the URL suffix, the way the beta list is computed, the session header (Claude Code's own, or a keyed hash for Codex) and the account header (`ChatGPT-Account-ID` from the first of `workspaceId`, `chatgptAccountId`, `accountId` that the account holds). The pipeline computes the values and the request headers it reads are an allow-list (`pipeline.PickHeaders`), so a client header cannot reach an upstream. A Codex request now carries the right headers but still the pre-1.10 body, so it will likely be refused until 1.10.

**1.10c built: the device flow and GitHub Copilot.** A device login is one more kind of session in the existing store, so the same binding, the same single use and the same read-once outcome apply. The poll gate lives in the store (`Sessions.Poll`), not in the handler: it hands the login to one caller and keeps the provider's interval, so the browser's own timer cannot make the router call GitHub faster than GitHub allows. GitHub answers a pending poll with a 200 body, so the body is read before the status. The finished-login check had to sit in the gate too: a login that already ended answers through the status read, not as `pending`.

**The login token and the chat token are two secrets.** Only the minted Copilot token leaves for the chat endpoint, and the pipeline asks the minter, not the stored account, for it. A key added by hand to the same provider keeps its own scheme and never meets the minter (a test pins it).

**Not verified without a live account:** that GitHub still accepts the 0.38.0 editor headers on the mint and the chat endpoints, which `gpt-*` ids need `/responses`, and whether it issues refresh tokens for this client id (the login stores one only if it is sent).

**The session sent to Codex is never the client's.** A keyed hash of the session and the account is sent, so one client cannot choose the value another client's conversation uses (PRD 11).

**1.10e built: the code-flow logins.** A login is now one of three kinds in the same engine: `code-pkce` (claude, codex, xai, gitlab), `code` with no PKCE (cline, clinepass) and `device`. What differs is data (`redirect`, `redirectHost`, `params` with placeholders, `appFromAccount`, `pat`, `refresh.url`) and, for Cline, a code dialect that reads the tokens out of the code itself. A test keeps every dialect and hook name equal to its table.

**The OAuth application of a GitLab account lives with the account.** The secret travels only in the body of the start request, stays in the memory session, and is stored sealed in provider data, so the refresher rebuilds the flow from the account and a renewal needs no configuration. An account that lost its application cannot be renewed. Nothing returns the secret or puts it in an address, a log or an error.

**A server address is held to a bare https origin twice**: when the login starts and again when a chat request is sent, so a stored value that was altered still cannot send a token to a path, a userinfo or plain http.

**The `public` redirect needs the dashboard at the `APP_URL` origin.** The session cookie must reach `/callback`, so a dashboard opened at another address finishes by pasting the landing address.

**Not verified without a live account:** that Cline accepts the `public` redirect and the fixed-word identity headers, that it echoes `state`, that GitLab accepts the application on the public redirect and a pasted token as a bearer on chat, and that xAI accepts the `nonce`, `plan` and `referrer` parameters.
